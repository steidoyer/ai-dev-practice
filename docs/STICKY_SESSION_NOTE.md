## 핵심 개념 — "한 속성을 움직이는 길이 두 종류다"

framer-motion에서 x나 opacity 같은 속성을 움직이는 방법은 성격이 완전히 다른 두 시스템이 있어요. 이걸 같은 속성에 겹쳐 쓴 게 지금 상황입니다.

**① 선언형 (목표 상태를 적는 방식) — initial / whileInView + transition**
- "여기서 시작 → 저기로 도착"만 적으면, framer-motion이 그 사이를 시간(duration)에 맞춰 스스로 채워 줍니다.
- **운전대를 잡은 건 "시간"**입니다. 뷰에 들어온 순간부터 0.8초 동안 알아서 이동.
- 예: initial 0 → whileInView 1 = "뷰에 들어오면 0.8초간 페이드인 해줘."

**② 값 구동 (외부 값에 직접 매다는 방식) — style={{ x }} (x는 useTransform 결과)**
- 값이 스크롤 위치에 매 프레임 직접 매달립니다. 스크롤 30%면 그에 해당하는 값, 되감으면 값도 되감김.
- **운전대를 잡은 건 "스크롤"**입니다. 시간이 아니에요.

**문제**: 지금 원의 x는 ①(whileInView x:0)과 ②(style x) 둘 다 지정돼 있어요. 그럼 "이 x 값을 시간이 정할래, 스크롤이 정할래?" 하고 운전대를 둘이 잡는 셈이라, 서로 밀어내서 의도대로 안 움직입니다. (누가 이기는지는 공식 문서도 규정 안 해서 신뢰할 수 없어요 — 그래서 "이기게 만들기"가 아니라 한 속성엔 운전자를 하나만 두는 게 정답입니다.)

**opacity: 1은 세 번째 경우** — 이건 MotionValue도 아니고 그냥 고정 숫자예요. 애니메이션도 스크롤도 아닌 "무조건 1"이라, initial 0 → whileInView 1 페이드가 나타날 자리를 덮어버려서 페이드가 안 보입니다. "왜 등장 페이드가 안 먹지?"의 흔한 원인이에요.

그래서 결정할 건 **속성마다 운전자 하나 고르기**입니다: 병합은 스크롤이 몰기로 했으니(기획 §3) → x/y는 ②만 남기고, opacity는 "스크롤에 걸지 / 진입 1회 페이드로 둘지" 하나만 고르면, 나머지는 자연히 지울 것들이 됩니다.

## 대화 1

**개발자:** 지금은 중복지정 지워진 상태 맞지?

**리뷰어:** 네, 지금 상태를 속성별로 짚어보면 — **핵심이었던 "한 속성을 두 애니메이션 드라이버가 동시에 무는" 이중 지정은 사실상 해소된 상태**가 맞습니다. 다만 완전히 깨끗해진 건 아니라서 나눠서 봐 드릴게요.

현재 안쪽 원 `motion.div`에서 살아있는 것과 주석 처리된 것:

| 속성 | `initial` | `whileInView`/`animate` | `transition` | `style` | 지금 실제 드라이버 |
|---|---|---|---|---|---|
| x | `-80`(살아있음) | 주석 | 주석 | MotionValue `x`(살아있음) | **style 하나** |
| y | `-80`(살아있음) | 주석 | 주석 | MotionValue `y`(살아있음) | **style 하나** |
| opacity | `0`(살아있음) | 주석 | 주석 | 리터럴 `1`(살아있음) | **style 하나(고정)** |

이전 문제는 `initial → whileInView` + `transition`(선언형·시간 구동)과 `style`의 MotionValue(값·스크롤 구동)가 x·y·opacity 각각을 동시에 물고 있던 것이었죠. 지금은 `whileInView`·`animate`·`transition`이 전부 주석 처리돼서, 각 속성을 실제로 매 프레임 그리는 주체는 **`style` 하나**로 정리됐습니다. 그래서 "운전대를 둘이 잡는" 충돌 자체는 없어졌습니다.

다만 **드라이버는 아니지만 남아서 겉도는 선언들**이 있습니다 — 이건 충돌이라기보단 "죽은 코드/의도 확인이 필요한 부분"입니다:

- **`initial`의 값들**: `animate`류가 없으니 `initial`은 "애니메이션 시작점"으로서의 역할이 사라졌습니다. x·y는 스크롤 0 지점에서 어차피 `-80`이라 결과가 겹쳐 보일 뿐, `style` MotionValue가 실제 렌더 소스입니다. opacity `0`은 `style`의 리터럴 `1`에 덮여 화면엔 안 나타나고요.
- **`opacity: 1` 리터럴**: 값이 고정돼 있어서, 만약 페이드인을 다시 살리고 싶다면 이 리터럴이 그걸 막습니다.
- **`viewport={{ once: true }}`**: 짝이 되는 `whileInView`가 주석 처리돼서 지금은 아무 일도 하지 않는 고아 prop입니다.

한 가지만 스스로 확인해 보시면 좋겠습니다 — 지금은 `style`의 MotionValue만 살아있으니 원이 스크롤 위치에 따라 움직입니다. 그런데 opacity는 `1`로 고정돼 있죠. 페이드인(서서히 나타남)을 넣을 생각이신가요, 아니면 처음부터 보인 채 위치만 움직이는 게 의도인가요?

*(주: 이 답변은 리뷰어가 참조한 낡은 파일 스냅샷 기준이었다. 실제로는 opacity 관련 선언이 이미 삭제된 상태였고, 아래 대화 3에서 정정된다.)*

## 대화 3

**개발자:** 근데 지금 opacity 1 다 지우지 않았어? 내가 안보이는데 어딘지 설명해줘

**리뷰어:** *(파일을 다시 읽어 확인한 뒤)*

맞습니다 — 제가 방금 전 답변에서 참고한 건 **이전에 읽어둔(오래된) 버전**이었습니다. 지금 다시 읽어보니 `opacity: 1`은 **이미 지워지셨네요.** 제 직전 설명이 낡은 스냅샷 기준이었습니다. 혼동드려 죄송합니다.

현재 실제 상태:

```
// initial=...        ← 주석
// whileInView=...     ← 주석
// animate=...         ← 주석
// viewport=...        ← 주석
// transition=...      ← 주석
style={{ x, y }}       ← 이것만 살아있음 (opacity 없음)
```

그러니까 지금은:

- **`opacity: 1` 리터럴 → 없어졌습니다.** 그래서 원의 투명도는 이제 어떤 드라이버도 건드리지 않으니 CSS 기본값(불투명, 1)으로 그냥 보이는 상태입니다.
- **`style`가 실제로 구동하는 건 `x`, `y` 두 개뿐**입니다. 둘 다 스크롤(`useTransform(scrollYProgress, ...)`) 값이라 스크롤 위치에 따라 움직입니다.
- 주석 처리된 `initial`·`whileInView`·`animate`·`viewport`·`transition`은 지금 아무 역할도 안 합니다 (잔여 주석).

정리하면, **"opacity 중복/고정" 문제는 완전히 사라진 상태가 맞습니다.** 남은 건 `x`·`y`를 `style`(스크롤 값)만으로 구동하는 깔끔한 단일 드라이버 구조입니다.

혹시 페이드인을 원래 의도하셨다면, 지금은 opacity를 아무도 안 건드리니 처음부터 불투명하게 바로 보일 겁니다 — 이 부분만 의도대로인지 확인해 보시면 되겠습니다.

## 대화 4

**개발자:** 일단 섹션을 sticky로 고정했는데 이후에 뭘로 풀어가야할지 모르겠어 어떤걸 참고하면 될까

**리뷰어:** *(현재 코드와 `SCROLL_MERGE_GUIDE.md`, `page.tsx` 구조를 확인한 뒤)*

코드를 보니 지금 sticky를 **섹션(`<section>`) 자체**에 거셨네요(`md:sticky md:top-0`). 그리고 페이지에서 `<Approach />`는 다른 섹션들(`Hero`, `Projects`, `Skills`, `CTA`)과 **나란히 형제**로 놓여 있습니다.

### 지금 상태에서 sticky가 처한 문제

`position: sticky`는 **"자기 부모(컨테이닝 블록) 박스 안에서만" 붙어 있다가, 그 부모를 다 지나가면 놓여납니다.** 그런데 지금 섹션의 부모는 사실상 **페이지 전체**입니다. 그래서 두 가지가 어긋납니다:

1. **"얼마나 붙어 있을지"를 정하는 주체가 없습니다.** 섹션이 top:0에 붙으면, 놓여나는 시점은 *페이지가 끝날 때*가 됩니다. 즉 Projects·Skills·CTA를 스크롤하는 내내 Approach가 화면에 붙박여 뒤 섹션과 겹칠 수 있습니다. → "붙긴 붙는데 언제 떨어질지 통제가 안 되는" 느낌이 이것 때문입니다.
2. **병합이 진행될 "스크롤 거리"가 여전히 없습니다.** 섹션 높이는 `py-canvas` 보통 높이라, `useScroll`의 진행도 0→1이 흐를 물리적 공간이 사실상 순식간입니다. (가이드에서 말한 ⭐B 문제 — 아직 안 풀린 상태)

### 핵심 개념: "거리 담당"과 "고정 담당"을 분리해야 합니다

`SCROLL_MERGE_GUIDE.md` §3.2.1에 정리해 둔 뼈대가 바로 이겁니다:

```
바깥 요소 (tall)      ← 세로로 길다. 이 "길이" = 병합이 진행될 스크롤 거리 (B의 답)
  └ 안쪽 요소 (sticky) ← top:0로 뷰포트에 고정 (사용자 눈엔 "화면 멈춤")
       └ 원 3개
```

지금은 이 **두 역할을 섹션 하나가 겸하려다** 둘 다 애매해진 상태입니다. sticky는 "혼자서는" 아무 거리도 만들지 못합니다 — **자기보다 키가 큰 부모를 지나가는 동안**에만 붙어 있는 것이라, 그 "키 큰 부모"를 따로 만들어 줘야 비로소 의미가 생깁니다.

그리고 하나 더 — **`useScroll`의 `target`은 "고정된 요소(sticky)"가 아니라 "거리를 만드는 요소(tall 바깥)"를 가리켜야** 진행도가 직관적으로 흐릅니다. 지금은 target이 sticky 걸린 섹션 자신이라, "붙박여 안 움직이는 요소"를 기준으로 진행도를 재는 셈이 됩니다.

### 참고할 곳 (순서대로)

1. **`SCROLL_MERGE_GUIDE.md` §3.2.1** — 지금 상황 정확히 그 절입니다. tall 바깥 + sticky 안쪽 2겹 구조, target/offset 연결 방식이 글로 다 있습니다.
2. **§4-3** — "스크롤 거리 확보(B): 섹션 `min-height`를 키울지 / sticky로 갈지"의 선택지 정리.
3. **§5-3** — 권장 구현 순서 중 "B 확보" 단계.
4. 공식 문서: **Motion — React scroll animations**(https://motion.dev/docs/react-scroll-animations)에 sticky 패턴 설명, **useScroll**(https://motion.dev/docs/react-use-scroll)에서 `target`/`offset`을 문서 대조.

### 스스로 확인해 보실 질문

- **병합이 "얼마 동안"(몇 화면분 스크롤) 진행되면 좋겠나요?** 그 길이가 곧 바깥 tall 요소의 높이(예: `200vh`)가 됩니다.
- **sticky를 섹션 전체에 걸까요, 아니면 원이 든 안쪽 박스에만 걸까요?**
- **`useScroll`의 `target`을 지금처럼 sticky 요소에 둘까요, 아니면 거리를 만드는 tall 요소로 옮길까요?**

이 세 가지 답이 나오면 구조가 자연스럽게 정해집니다. 다만 구현(마크업/클래스) 자체는 직접 손코딩하시는 부분이라 코드는 제안만 드리고 작성은 하지 않겠습니다.

## 추가 — A vs B(스크롤 되감김) & sticky 가능 여부 (2026-07-31 대화)

> *대화 8 이후 여러 대화(헤더 토큰, `useTransform` 배열, Rules of Hooks 등)가 있었으나, 여기엔 요청에 따라 **"A vs B 차이"와 "sticky 가능 여부" 두 대화만** 있는 그대로 추가한다. 앞의 코드 리뷰 부분은 생략.*

### 대화 A — 스크롤 내려간 뒤 올라갈 때 애니메이션 안 하게

**개발자:** 코드 한번 봐줘 그리고 스크롤 내려간 뒤에 다시 올라갈때는 애니메이션 동작 안하게 하고싶어

**리뷰어:** *(앞부분 코드 리뷰는 생략, 아래는 요청 관련 설명 원문 그대로)*

## 요청: "내려갈 땐 되고, 올라갈 땐 애니메이션 안 함"

### 왜 지금은 올라갈 때 되감기는가 (개념)

지금 애니메이션은 **값 구동(scrollYProgress에 직접 매달림)**입니다. 이 방식의 본질이 **양방향**이에요 — 스크롤을 내리면 progress가 0→1로 커지며 원이 모이고, **올리면 progress가 1→0으로 작아지며 그대로 되감깁니다.** 즉 "올라갈 때 안 되감기게"는 값 구동의 기본 성질과 정면으로 부딪히는 요구라, **한 번 재생 후 고정(latch)** 하는 장치를 따로 넣어야 합니다.

방법은 크게 둘입니다.

### A. 진행도를 "한 번 올라가면 안 내려오는 값"으로 바꾸기 (스크롤 스크럽 유지) — 권장

`scrollYProgress`를 transform에 직접 넣지 말고, **여태 도달한 최댓값만 기억하는 진행도**를 하나 만들어 그걸 넣는 겁니다(단조 증가). 개념 흐름:

- `useMotionValue(0)`로 `latched` 값을 하나 만들고,
- `useMotionValueEvent(scrollYProgress, "change", v => { if (v > latched.get()) latched.set(v) })`로 **더 커질 때만** 갱신,
- `useTransform`들의 입력을 `scrollYProgress` → `latched`로 교체.

이러면 내려갈 땐 지금처럼 스크롤에 맞춰 진행되고(스크럽 유지), **올라가도 latched는 최고점에서 안 내려와** 원이 모인 상태로 멈춰 있습니다. 지금 sticky+스크롤 구조를 **그대로 두고** 드라이버만 단조 증가로 바꾸는 방식이라, 투자하신 구조가 안 깨집니다.

### B. 선언형 `whileInView` + `viewport={{ once: true }}`로 전환 (한 번 재생)

framer-motion에는 "뷰 들어오면 1회만, 되감기 없음"이 내장돼 있습니다(`once: true`). 다만 이건 **시간 구동**이라, 스크롤에 맞춰 스크럽되던 병합이 **뷰 진입 시 0.8초 재생**으로 성격이 바뀝니다. 그러면 지금의 **sticky+tall(120rem) 스크롤 거리 구조가 무의미**해집니다(스크롤로 몰 필요가 없어지니까). 즉 이 방향은 지금까지 만든 스크롤 병합을 상당 부분 걷어내는 선택입니다.

### 정리

- **스크롤로 원이 모이는 지금 느낌을 유지**하고 싶다 → **A(latched 진행도)**. 드라이버만 단조 증가로 바꾸면 됨.
- **"뷰 들어오면 한 번 재생"으로 성격을 바꿔도 된다** → B. 단, sticky/tall 구조 상당수가 불필요해짐.

두 방식은 지난 §3.1(선언형 vs 값 구동) 프레임 그대로입니다 — A는 값 구동을 유지하되 값을 단조화, B는 아예 선언형(once)으로 전환.

## 확인할 것

1. **A와 B 중 어느 느낌**을 원하시나요? (스크럽 유지 = A / 진입 1회 재생 = B)
2. reduced-motion(`useReducedMotion` 지금 import만 됨) — 접근성상 모션 최소화 사용자에겐 **처음부터 합쳐진 최종형**을 보여주기로 계획(§3 E)했었죠. A/B 어느 쪽으로 가든 이 분기도 곧 넣어야 합니다. 지금 같이 설계할까요, 나중에 볼까요?

구현 코드는 직접 하시는 부분이라, A의 방식(단조 증가 진행도)은 **개념·API 흐름만** 짚었습니다. 어느 쪽으로 가실지 정하시면 그 방향 개념을 더 풀어드리겠습니다.

### 대화 B — B로 가도 sticky 효과가 가능한가

**개발자:** 일단 2번은 나중에보고 만약 a, b에서 b로 가도 sticky 처럼 효과는 가능한거야?

**리뷰어:** 좋은 질문입니다. 핵심은 **"sticky(고정)"와 "스크롤에 맞춰 애니메이션이 진행되는 것"은 서로 다른 두 가지**라는 점입니다. 이걸 나눠 보면 답이 명확해집니다.

## sticky 자체는 B로 가도 됩니다 (독립적이니까)

`position: sticky`는 **순수 CSS 레이아웃**이라 framer-motion이나 애니메이션 드라이버와 **아무 상관이 없습니다.** 그냥 "요소를 뷰포트에 붙여 둔다"일 뿐이에요. 그래서 B(`whileInView` + `once`)로 가도 `md:sticky md:top-20`은 그대로 두면 **원이 화면에 고정되는 것 자체는 됩니다.** 이건 확실합니다.

## 다만 — "고정"은 되지만 "스크롤을 따라 진행"은 안 됩니다

여기가 핵심 차이입니다. 지금 느낌은 두 개가 합쳐진 겁니다:
- **고정** (sticky) + **스크롤에 맞춰 원이 모임** (값 구동/스크럽)

B로 가면 앞의 "고정"은 유지되지만, 뒤의 "스크롤에 맞춰 진행"이 사라집니다. B는 **뷰에 들어온 순간 0.8초 동안 알아서 1회 재생**하는 시간 구동이라, 스크롤 위치와 무관하게 스스로 굴러갑니다.

## 그래서 B + 지금의 tall/sticky는 궁합이 안 좋습니다

지금 섹션이 `md:h-[120rem]`로 긴 이유는 **스크롤 스크럽에 쓸 거리**를 확보하려던 거였죠. 그런데 B는 그 거리를 **안 씁니다**(시간이 몰지, 스크롤이 몰지 않으니까). 결과를 상상하면:

- 섹션에 들어오면 원이 0.8초 만에 한 번 합쳐지고,
- 그 뒤로 **남은 ~100rem을 스크롤하는 내내 원은 고정된 채 아무 일도 안 함.**

즉 "고정은 됐는데 그 긴 구간이 텅 빈" 어색한 스크롤이 됩니다. **B는 보통 높이 섹션(tall 없이)에 어울립니다.**

## 정리 — 원하시는 효과가 무엇이냐로 갈립니다

| 원하는 것 | 맞는 선택 |
|---|---|
| 고정 + **스크롤 따라 원이 모임** + 올라갈 때 안 되감김 | **A** (latched 값) |
| 고정 + 진입 시 **1회 재생**(스크롤 안 따라감) | B — 단, tall(120rem)은 걷어내고 보통 높이로 |
| 스크롤 스크럽은 필요 없고 그냥 한 번 재생 | B (sticky도 굳이 필요 없을 수 있음) |

**"지금처럼 스크롤에 맞춰 원이 모이는 느낌"을 유지하면서 올라갈 때만 안 되감기고 싶다** — 이게 목적이라면 그건 정확히 **A**입니다. B는 그 "스크롤 따라 모임"을 포기하는 대신 "1회 재생"을 얻는 트레이드오프예요.

그래서 되묻자면 — **원이 스크롤을 따라 서서히 모이는 그 느낌 자체를 유지하고 싶으신가요?** 그렇다면 A가 답이고, "그 느낌은 없어도 되고 한 번 딱 나타나면 된다"면 B로 가되 tall 높이를 정리하는 방향입니다. 어느 쪽이 원하시는 그림인가요?
