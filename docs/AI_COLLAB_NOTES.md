# AI 협업 노트 (Claude Code와 일하는 법)

AI 도구(Claude Code 등)와 개발을 **협업**하며 얻은, 코드가 아닌 **일하는 방식**에 대한 노트.
특정 버그·기법이 아니라 "AI와 어떻게 결정하고 개선을 녹여낼지"를 다룬다.
(기술 사용법은 각 가이드, 코드 리뷰 이력은 `CODE_REVIEW_LOG.md`, 작업 기록은 `WORK_LOG.md`.)

## 이 문서의 목적

- 지금은 한 세션에서 멘토·리뷰·설명·문서화를 **한 AI**가 겸한다. 이후 **하네스 방식으로 에이전트를 분리**(개발 멘토링 / 코드 리뷰 / 디자인 등을 별개 에이전트)해 협업할 계획이며, 그때 각 에이전트가 참고할 **협업 원칙**을 여기 모은다.
- 세션 대화는 압축·소멸되므로, 대화에서 나온 **일하는 방식의 교훈**을 코드 밖 문서로 남긴다.

## 배경 관점 (개발자 정리)

- **개선 사항이 나중에 나오는 것은 AI가 없어도 동일한 현상**이다. 개발 후 리팩터링·개선은 정상적이고 필요한 과정이다.
- 따라서 과제는 "개선이 안 나오게 하는 것"이 아니라, **그 개선 과정을 AI 협업 안에 어떻게 자연스럽게 녹여낼지**다.
- 좋은 개선이 **뒤늦게** 나오지 않도록 **처음부터 효율을 높이는 방법**을 함께 찾는다.

## 핵심 교훈

### 1. 횡단 관심사는 "근원 vs 잎"을 먼저 물어라
reduced-motion·테마·i18n처럼 여러 곳에 걸치는(cross-cutting) 처리를 붙일 땐,
**단일 근원(드라이버)에서 한 번 막을지, 말단(잎)마다 막을지**를 먼저 명시적으로 판단한다.
값 구동이 하나의 입력으로 모이면(예: 스크롤 `latched` → 여러 `useTransform`),
그 **근원 하나를 최종값으로 고정**하는 편이 잎마다 분기하는 것보다 수정 지점이 적고 빠뜨림이 없다.
(단, 근원 가드는 잎에서 안 보여 **덜 지역적**이므로 드라이버 옆 주석으로 보완.)

### 2. 불을 끈 직후 "이제 구조가 최단인가?" 전용 패스
버그를 잡는 프레임에서 나온 해법은 **"동작하는 첫 패턴"에 멈추기 쉽다.**
급한 불(예: 하이드레이션 오류)을 끄고 나면, 곧바로 다음 것을 짓기 전에
**"지금 이 구조가 가장 단순한가?"**를 따지는 짧은 리뷰를 별도로 넣는다.

### 3. 대안을 명시적으로 요구하라
AI 멘토는 시간 압박·문제 해결 프레임 안에서 **첫 동작 패턴으로 수렴**하는 경향이 있다.
"단일 지점으로 하는 방법은 없나?", "이 구조 말고 다른 선택지는?"처럼
**대안을 명시적으로 물으면** 더 나은 구조가 앞당겨 나온다.
반대로 AI(멘토 역할)는 개발자가 묻지 않아도 **대안을 먼저 제시**하는 것을 기본으로 삼는다.

### 사례 — Approach 섹션 reduced-motion 가드 (A vs B)
- **A (근원 가드)**: `latched`를 1로 고정 → 파생 `useTransform`이 전부 최종형. 수정 한 곳.
- **B (잎 가드)**: 속성마다 `reduce ? 최종 : mv`. 명시적이나 장황·누락 위험.
- A가 B의 결과를 **정확히 재현**하는데도 당시 A가 제시되지 않았다. 이유를 이력에서 확인:
  - 그때 실제로 풀던 것은 "우아한 가드"가 아니라 **SSR 하이드레이션 버그**였고(`WORK_LOG.md`),
    그 버그가 **Hero·FadeIn·Approach 셋에 동시**로 터졌다.
  - 해법이 세 컴포넌트를 **동시에** 만족해야 했다 → 공통분모 = "SSR-안전 훅 + 잎마다 분기(B)".
    A(단일 드라이버 고정)는 선언형인 Hero/FadeIn엔 적용조차 안 돼 **후보에 오르지 못했다.**
  - 검토된 선택지 자체가 ①`MotionConfig`(스크롤 값엔 안 걸려 기각) ②`useReducedMotionSafe` 잎 분기 둘뿐이었고,
    불을 끈 뒤 **"latched 부분만 보면 근원 가드가 더 단순한가?"** 재검토 패스가 없었다.
- **결론**: B가 Approach에 더 맞아서가 아니라, **그때의 진짜 문제(3곳 하이드레이션)에 옳은 통합 해법이 B였고**,
  latched 부분에 한정한 더 단순한 구조(A)를 되돌아보지 않은 것. → 위 교훈 1·2·3의 근거.

## 멀티 에이전트(하네스)로 녹여내기

에이전트를 분리할 때, 위 교훈을 **역할 설계**로 옮긴다.

- **리뷰/아키텍처 에이전트를 "불 끈 뒤"에 별도로 돌린다.** 기능이 동작한 직후,
  버그 프레임에 갇히지 않은 **신선한** 에이전트가 "근원 vs 잎", "이 구조가 최단인가"를 점검한다.
  (같은 에이전트가 구현과 재검토를 겸하면 터널 비전에 빠지기 쉽다 — 분리의 실익.)
- **멘토 에이전트는 대안 제시를 기본 행동으로.** 첫 동작 패턴만 주지 말고,
  단일 지점 해법·구조적 선택지를 함께 제시한다(개발자가 안 물어도).
- **결정의 "당시 제약"을 함께 기록한다.** 나중의 리팩터링이 과거 결정을 "그때가 틀렸다"가 아니라
  **"제약이 이랬고 지금은 바뀌었다"**로 이해하도록, 왜 그 선택을 했는지의 맥락을 남긴다(이 문서·`WORK_LOG.md`가 그 역할).
- **횡단 관심사 체크리스트**를 리뷰 에이전트가 든다: 새 애니메이션/상태를 추가할 때
  reduced-motion·반응형·접근성 가드를 **근원에서** 처리할 수 있는지 먼저 확인.
