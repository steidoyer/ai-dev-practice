# 작업본(clone) 이후 로드맵 — 직접 코딩 & AI 멘토 모드

이 문서는 현재 프로젝트를 **내 컴퓨터의 새 로컬 폴더로 clone한 작업본에서 직접 손으로 개발**해 나갈 때의
작업 순서와 **AI 역할 규칙**을 정리한다. (이 프로젝트는 AI 지시로 만들어졌고, 다음 단계는
개발 실력 향상을 위해 **내가 직접 코딩**하는 것이 목적이다.)

---

## 0. AI 역할 규칙 (가장 중요 — 먼저 읽기)

다음 단계부터 AI는 **리뷰어이자 멘토**로만 동작한다.

**하는 것**
- 지금 내가 **무슨 작업을 해야 하는지**(할 일 목록/범위) 알려준다.
- 내가 막힌 부분을 물으면 **개념을 설명**하고, 그 내용을 담은 **문서를 만들어** 준다.
- 내가 **놓치고 있는 지점을 질문/힌트로 짚어** 스스로 생각하게 유도한다.
- 코드를 **읽고 리뷰**한다(무엇이 왜 문제가 될 수 있는지 관점 제시).

**하지 않는 것 (금지)**
- 코드를 **직접 작성하거나 수정하지 않는다.** (스니펫으로 정답 코드를 주는 것도 금지)
- **수정 방향을 직접 지시하지 않는다.** "이렇게 고쳐라"가 아니라 "여기서 무엇을 의심해볼 수 있을까?"로.
- 정답을 앞질러 말해 **스스로 도달할 기회를 뺏지 않는다.**

**요청 방식(내가 AI에게 말하는 법) 예시**
- "이번에 뭘 해야 해?" → AI: 할 일 목록/범위 제시(방법은 내가 찾음).
- "이 부분이 왜 안 될까? 힌트만 줘." → AI: 관련 개념 설명 + 생각할 질문 + (필요 시) 문서화. 정답 코드 X.
- "내 코드 리뷰해줘." → AI: 관점·우려 지점 지적, 고칠 코드는 안 줌.

> **단계별 AI 관여 범위(확인 필요):** 아래 1~3단계(직접 손코딩)는 **엄격 멘토 모드**로 둔다.
> 4(OG 이미지)·5(성능·배포)는 코딩 실력 향상 대상이 아닐 수 있어, 여기서도 멘토 모드를 유지할지
> 아니면 AI가 실작업을 도와도 되는지는 **그 단계 진입 시 내가 정한다.** (기본값: 멘토 모드 유지)

## 1단계. 저장소 준비 (GitHub 업로드 + 작업본 확보)

**결정된 전략 (→ PROJECT_PLAYBOOK.md 의사결정)**: GitHub **원격 저장소는 `ai-dev-practice` 1개**만 둔다(repo를 2개 만들지 않음).
분리하는 건 저장소가 아니라 **내 컴퓨터 안의 작업 폴더**다. 즉,
GitHub에 올린 뒤 baseline 시점에 **`ai-only` 태그**로 스냅샷을 찍고,
그 원격 저장소를 **내 로컬의 다른 경로(새 로컬 폴더)에 `git clone`** 해서 거기서 직접 개발한다.

정리하면 구성은 이렇게 된다:
- **GitHub `ai-dev-practice`** — 원격 저장소(하나뿐). 원본과 작업 결과가 모두 여기로 push됨.
- **지금 이 로컬 폴더**(`my-portfolio-page`) — 최초 push의 출처. `ai-only` 태그가 가리키는 baseline 상태.
- **새 로컬 폴더**(예: `ai-dev-practice-work` 같은 다른 경로) — 위 원격을 `git clone`한 **별도 작업 폴더**. 앞으로의 직접 코딩은 **여기서만** 한다.

두 로컬 폴더는 **같은 하나의 GitHub 저장소**를 바라보는 서로 다른 작업 디렉터리일 뿐이다(별도 repo·fork 관계 아님).

**할 일**
- [ ] 현재 프로젝트를 GitHub 원격 저장소(`ai-dev-practice`)로 push. *(작성 시점 기준 아직 커밋/원격 없음 — 전부 uncommitted)*
- [ ] baseline 시점에 `ai-only` 태그를 찍어 원본 상태 스냅샷 보존.
- [ ] 내 컴퓨터의 **다른 경로에 새 폴더를 만들어** 그 원격을 `git clone` → 이 새 로컬 폴더에서 직접 코딩(지금 폴더는 baseline으로 보존, 손대지 않음).

**왜 이 방식인가 (GitHub는 자기 계정의 자기 저장소를 같은 계정으로 fork 불가)**
별도 repo/진짜 fork는 이 목적(개인 실습 + baseline 대비)에 굳이 필요 없다.
원격 1개 + 태그 + 로컬 작업 폴더 분리면 원본 대비 diff도 명확하고 작업 환경도 깔끔히 분리된다.
(참고로 검토했던 다른 선택지: Template repository로 새 repo 생성, 새 빈 repo에 push, 다른 계정으로 fork, 새 브랜치에서 개발 — 모두 채택하지 않음.)

**막히면 물어볼 만한 것**: "태그와 브랜치로 baseline을 남기는 건 뭐가 다르지?", "같은 원격을 clone한 두 로컬 폴더는 서로 어떻게 동기화되지?"

## 2단계. 사전 정비 (섹션 제작 전 전반 작업)

새 섹션을 붙이기 전에 기반을 내가 원하는 형태로 정리한다. **순서는 유동적**(섹션 제작과 오갈 수 있음).

**할 일 (영역만 제시 — 구체 수정은 직접 점검·판단)**
- [ ] **Tailwind 클래스명/토큰 정리** — 지금 시맨틱 토큰 이름(`bg-bg`, `p-card`, `text-section` 등)과 유틸리티 사용이 내 기준에 맞는지 점검하고 원하는 대로 재정비.
- [ ] 컴포넌트 구조/네이밍/폴더 규칙 중 바꾸고 싶은 부분 정리.
- [ ] 기존 코드에서 **개선하고 싶은 부분** 목록화(직접 개선).

**막히면 물어볼 만한 것**: "이 토큰 네이밍이 관례상 괜찮은가?", "이렇게 바꾸면 어떤 부작용을 생각해봐야 할까?" → AI는 관점·체크포인트 제시, 코드 수정 X.

> 참고 자료(이미 있는 문서): 토큰/유틸 생성 원리 `DEV_QNA.md` Q3~Q6, 컨벤션 `CLAUDE.md`.

## 3단계. 새 섹션 2개 제작 (핵심 — 직접 손코딩)

이 프로젝트에서 실력 향상의 **메인 목표**. 두 개 정도의 새 섹션을 처음부터 직접 작성.

**할 일 (내가 주도)**
- [ ] 추가할 섹션 2개의 **목적/콘텐츠/레이아웃** 기획.
- [ ] 마크업 → 스타일(Tailwind) → 인터랙션 순으로 직접 구현.
- [ ] 기존 규칙 준수: 섹션 앵커 `id`, `container-page`, 디자인 토큰만 사용, 반응형(모바일 우선), 접근성 기준.
- [ ] Header 네비/앵커, 헤딩 계층(h2), 필요 시 framer-motion 등장(재사용 래퍼) 연동.

**AI에게 기대하는 서포트**
- 착수 전: "이 섹션에서 내가 결정하고 구현해야 할 항목이 뭐가 있어?" → 체크리스트.
- 구현 중 막힘: 개념 설명 + 생각 유도 질문 + 문서화. **정답 코드/수정 방향 직접 지시는 없음.**
- 완료 후: "리뷰해줘" → 우려 지점·놓친 관점 지적(고친 코드 제공 X).

> 참고: 반응형 규칙·기준은 `CLAUDE.md`, 접근성 기준은 `A11Y_CHECKLIST.md`, 애니메이션 적용 방식(래퍼 vs 직접)은 `DEV_QNA.md` Q11.
> 기술별 사용법 가이드(직접 코딩용): framer-motion → `FRAMER_MOTION_GUIDE.md`, TypeScript → `TYPESCRIPT_GUIDE.md`, Next.js(App Router) → `NEXTJS_GUIDE.md`.
